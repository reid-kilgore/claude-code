# DeviceActivity / DeviceActivityMonitor — falsifiable claims with sources (as of mid-2026)

## 1. DeviceActivityCenter.startMonitoring + DeviceActivitySchedule

- **Claim: `DeviceActivitySchedule(intervalStart:intervalEnd:repeats:warningTime:)` is a calendar-based (DateComponents) schedule; `repeats` is "A Boolean value that indicates whether the schedule recurs"; `warningTime` is "Optional components that generate a warning prior to regularly scheduled events."** Source: [Apple docs — DeviceActivitySchedule](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule) (verified via the doc JSON endpoint). Confidence: Apple official doc.
- **Claim: The schedule's `warningTime` drives `intervalWillStartWarning`, `intervalWillEndWarning`, AND `eventWillReachThresholdWarning` — Apple: "You can create a warning time that the system uses to provide your app extension with callbacks whenever a schedule is about to start or end, or when an event is close to reaching its threshold."** Source: same DeviceActivitySchedule doc. Confidence: Apple official doc (exact quote).
- **Claim: Minimum interval length is 15 minutes; shorter intervals throw `DeviceActivityCenter.MonitoringError.intervalTooShort`.** The error case is officially documented ("The activity's schedule has an interval that is too short" — [intervalTooShort doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/intervaltooshort)), but the **15-minute figure is NOT in the Apple doc text** — it comes from community sources: [forum thread 729841](https://developer.apple.com/forums/thread/729841) ("The schedule interval is set for 15 minutes (the minimum)"), [letvar Medium part 3](https://letvar.medium.com/time-after-screen-time-part-3-the-device-activity-monitor-extension-284da931391b) ("minimum end interval of 15 minutes from the start date"), and a [dedicated Medium post on intervalTooShort](https://killlilwinters.medium.com/overcoming-monitoringerror-intervaltooshort-error-in-screentime-api-0f5256fac741). Confidence: multiple independent developer reports; the specific number is not Apple-documented.
- **Claim: Maximum interval is one week; longer throws `MonitoringError.intervalTooLong` ("The activity's schedule has an interval that is too long").** Error case: Apple official doc ([MonitoringError](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror)). The "one week" figure: [forum thread 729841](https://developer.apple.com/forums/thread/729841) ("from the documentation, the maximum schedule interval is a week") and [thread 742131 on multi-day schedules](https://developer.apple.com/forums/thread/742131). Confidence: multiple forum reports; I could not find the "week" figure in current Apple doc text — treat the exact bound as community-established.
- **Claim: Calling `startMonitoring` on an already-monitored activity name "overwrites the previous schedule and events."** Source: [startMonitoring doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:)). Confidence: Apple official doc — BUT see §5: on iOS 18+ developers report the overwrite path fails to re-fire `intervalDidStart` unless `stopMonitoring` is called first.
- **Claim: If the interval is already ongoing when you call `startMonitoring`, callbacks can begin immediately ("may begin receiving callbacks as soon as the system calls this method if the activity's scheduled interval is ongoing").** Source: same startMonitoring doc. Confidence: Apple official doc.
- **Claim: Apple explicitly warns that "Attempting to monitor too many activities or activities that are too tightly scheduled can cause this method to throw an error" and suggests using `warningTime` instead of many tightly-packed schedules.** Source: same startMonitoring doc. Confidence: Apple official doc.

## 2. DeviceActivityEvent + threshold

- **Claim: `threshold` is "The amount of time that results in a callback to a DeviceActivityMonitor" — cumulative usage of the union of the event's applications/categories/webDomains within the schedule's interval; when reached, `eventDidReachThreshold(_:activity:)` fires.** Sources: [DeviceActivityEvent init doc](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/init(applications:categories:webdomains:threshold:includespastactivity:)), [DeviceActivityMonitor doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor). Confidence: Apple official doc.
- **Claim: Usage accrued earlier in the interval counts toward the threshold even if you registered the event mid-interval (pre-iOS 17.4 default behavior). An Apple Frameworks Engineer confirmed: if a 1-minute-threshold event fires instantly, "the device has been used for 1 minute since the start of the schedule's interval (i.e. the start of the current day)… you must specify a different start time for the schedule."** Source: [forum thread 727970](https://developer.apple.com/forums/thread/727970) (Apr 2023, Apple Frameworks Engineer reply). Confidence: Apple engineer on official forum.
- **Claim: `includesPastActivity` was added in iOS 17.4 (init available iOS/iPadOS/Catalyst 17.4+). Apple: "if your app calls startMonitoring… at 1:30pm with a schedule of 1:00pm to 2:00pm, then this boolean determines whether any activity between 1:00 PM and 1:30 PM will contribute to its threshold."** Source: [init(…includesPastActivity:) doc](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/init(applications:categories:webdomains:threshold:includespastactivity:)). Confidence: Apple official doc.
- **Claim: `includesPastActivity: false` does not always establish a clean baseline — overcounting bugs reported in late iOS 17 and continuing into iOS 18.** Sources: [thread 763542 "DeviceActivityMonitor is overcounting screen time"](https://developer.apple.com/forums/thread/763542), [thread 762137 "How does the threshold work"](https://forums.developer.apple.com/forums/thread/762137). Confidence: multiple forum reports; version-dependent.
- **Claim: Small/short thresholds are unreliable — 1-minute thresholds firing at `intervalDidStart`, or (iOS 26) `eventDidReachThreshold` "called immediately (after a couple of seconds) instead of waiting for the threshold."** Sources: [thread 727970](https://developer.apple.com/forums/thread/727970), [iOS 26 regression thread 808470](https://developer.apple.com/forums/thread/808470). Confidence: multiple forum reports; no Apple-documented minimum threshold exists — the "unreliable below X" figure is folklore, flag as unverified beyond these symptom reports.
- **Claim: `eventWillReachThresholdWarning(_:activity:)` exists to warn before the threshold, gated on the schedule's `warningTime`.** Source: [DeviceActivityMonitor doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor). Confidence: Apple official doc.

## 3. Limits and errors

- **Claim: Max ~20 concurrently monitored activities per app (app + its extensions combined); exceeding throws `MonitoringError.excessiveActivities` ("The calling process is monitoring too many activities").** Sources: error case in [Apple docs](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/excessiveactivities); the number 20 from [forum thread 710915](https://developer.apple.com/forums/thread/710915) ("The maximum number of activities that can be monitored at one time by an app and its extensions is twenty") — answered by a forum participant, not clearly Apple staff — corroborated by [kingstinct/react-native-device-activity README](https://github.com/kingstinct/react-native-device-activity) ("There's a hard limit on 20 monitors at the same time") and [Yamada Medium "Limitations of Screen Time-Related APIs"](https://medium.com/@yosshi4486/limitations-of-screen-time-related-apis-3ebf7c371962). Confidence: multiple independent reports converge on 20; not in Apple doc text.
- **Claim: Full documented `MonitoringError` set: `excessiveActivities`, `intervalTooLong`, `intervalTooShort`, `invalidDateComponents` ("The schedule's date range is invalid"), `unauthorized` ("The calling process isn't authorized to monitor device activity").** Source: [MonitoringError doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror). Confidence: Apple official doc.
- **Claim: There is NO documented limit on events per activity; a direct question went unanswered on the forums.** Source: [thread 681955 "Limits on monitoring events"](https://developer.apple.com/forums/thread/681955) (0 replies). Confidence: absence of evidence — flag as unknown, not "unlimited". (Related, different limit: ManagedSettings shielding caps at 50 application tokens per store — [riedel.wtf](https://riedel.wtf/state-of-the-screen-time-api-2024/).)
- **Claim: `startMonitoring` can also fail with XPC/connection errors to the `UsageTrackingAgent` service and occasional crashes inside the call.** Sources: [thread 682558](https://developer.apple.com/forums/thread/682558), [thread 770223](https://developer.apple.com/forums/thread/770223). Confidence: multiple forum reports.

## 4. DeviceActivityMonitor extension runtime

- **Claim: Extension point identifier is exactly `com.apple.deviceactivity.monitor-extension` (principal class = your `DeviceActivityMonitor` subclass); report extension is `com.apple.deviceactivityui.report-extension`.** Sources: [forum thread 681963](https://developer.apple.com/forums/thread/681963) — accepted answer from Apple staff (Systems Engineer); corroborated by 242 GitHub code hits (e.g., Provenance-Emu, expo-apple-targets docs). Confidence: Apple staff + widespread code evidence.
- **Claim: The extension is headless — spawned by the system (`deviceactivityd`) at schedule/threshold boundaries; it cannot present UI or foreground your app; its only real levers are ManagedSettingsStore writes (apply/remove shields and restrictions), app-group storage, local notifications.** Sources: [DeviceActivityMonitor doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor) — Apple's own sample code in the doc shows `let store = ManagedSettingsStore()` with the comment "You can use the `store` property to shield apps when an interval starts, ends, or meets a threshold"; [WWDC21 "Meet the Screen Time API"](https://developer.apple.com/videos/play/wwdc2021/10123/). Confidence: Apple official doc for the ManagedSettingsStore pattern; "cannot present UI/launch app" is Apple-design consensus (no API exists for it), widely reiterated ([riedel.wtf](https://riedel.wtf/state-of-the-screen-time-api-2024/) complains there is no API to open the parent app from shields).
- **Claim: Memory limit is 6 MB, enforced by jetsam — crash signature `EXC_RESOURCE (RESOURCE_TYPE_MEMORY: high watermark memory limit exceeded) (limit=6 MB)`; not increasable.** Sources: [forum thread 735454 "Memory limit for Device Activity Monitor"](https://developer.apple.com/forums/thread/735454) (exact jetsam string quoted by OP; community answer "there is no way to increase it"); [riedel.wtf (one sec developer)](https://riedel.wtf/state-of-the-screen-time-api-2024/) ("the 6 MB memory limit… frequently crashes due to memory pressure… even highly optimized implementations struggle"); [thread 724243](https://developer.apple.com/forums/thread/724243). Confidence: multiple concrete reports incl. crash-log evidence; the figure is NOT in Apple docs. Some older posts say "5-6MB" — the observed jetsam limit string says 6 MB.
- **Claim: Callbacks must finish fast; heavy work (UserDefaults churn, analytics, network) causes early termination. No official wall-clock number is documented — "a few seconds" is community folklore.** Sources: [thread 721945](https://developer.apple.com/forums/thread/721945) ("reading/writing to User Defaults and sending analytics events cause the callback functions to terminate early"); [thread 762540](https://developer.apple.com/forums/thread/762540). Confidence: multiple forum reports; the exact seconds figure is unverified — flag explicitly.

## 5. Reliability issues (the big one)

- **Claim: The system sometimes fails to launch the monitor extension at all for minutes-to-hours, silently dropping `intervalDidStart`/`intervalDidEnd`/threshold callbacks; strongly overrepresented on iOS 17.4+ vs iOS 16; logged as `access(...appex) failed with errno 2`; FB13556935.** Source: [thread 745035 "Device Activity Monitor Extension sometimes fails to launch"](https://developer.apple.com/forums/thread/745035) — includes cross-user analytics; quote: "This bug is CRITICAL for all apps relying on the Device Activity framework." Confidence: multiple developer reports with instrumentation; version-dependent (iOS 17.4+).
- **Claim: `eventDidReachThreshold` can arrive minutes-to-hours late, or batched — e.g., 1/2/3-hour notifications delivered simultaneously (iOS 17.5+); hypothesis on the thread: failed deliveries (jetsam'd extension) are retried at the NEXT threshold, piling up. Apple Frameworks Engineer asked for a bug report; no fix stated.** Sources: [thread 762540](https://developer.apple.com/forums/thread/762540), [thread 757310](https://developer.apple.com/forums/thread/757310), [thread 737741](https://developer.apple.com/forums/thread/737741), [thread 735293](https://developer.apple.com/forums/thread/735293). Confidence: multiple forum reports; version-dependent.
- **Claim: iOS 18 regression — re-calling `startMonitoring` on an already-monitored activity does NOT re-trigger `intervalDidStart` (contradicting the documented "overwrites" behavior); 100%-reproducible workaround is `stopMonitoring` first. FB14110789 / FB14187336.** Source: [thread 758309](https://developer.apple.com/forums/thread/758309). Confidence: multiple reports, reproducible; version-dependent (iOS 18 betas onward).
- **Claim: Monitoring registrations are believed to persist across reboot (schedules live in `deviceactivityd`, and `DeviceActivityCenter().activities` still returns them), but boundary callbacks around reboot/locked/Low-Power states are missed often enough that production apps (one sec, Habit Doom-style blockers) build defensive layers: chain short schedules, never schedule far out ("never schedule DeviceActivity more than 44 minutes out… schedules become unreliable beyond a 45-minute limit"), add 1-2 minute buffers, and re-assert state on app foreground.** Sources: [Habit Doom blog "Apple's Screen Time API: How It Broke Me"](https://habitdoom.com/blog/apple-screen-time-api-guide) (45-minute claim, buffer strategy, "blocking must survive… restarting their phone"); [riedel.wtf](https://riedel.wtf/state-of-the-screen-time-api-2024/); [kingstinct README](https://github.com/kingstinct/react-native-device-activity). Confidence: reboot persistence itself is NOT Apple-documented — I found no authoritative statement either way; the 45-minute figure is a single blog's empirical claim (unverified). The general "missed boundary callbacks → re-assert defensively" pattern is multi-source. Flag: "persists across reboot" = believed/likely, evidence weak.
- **Claim: Callbacks tied to usage events do not fire in the iOS Simulator because the Simulator doesn't track Screen Time usage (Settings > Screen Time shows nothing); schedule lifecycle may partially run but `eventDidReachThreshold` never does; physical device required.** Sources: [thread 746416](https://developer.apple.com/forums/thread/746416), [thread 685126 "Is the Screen Time API completely…"](https://developer.apple.com/forums/thread/685126), [pedroesli.com tutorial](http://pedroesli.com/2023-11-13-screen-time-api/). Confidence: multiple consistent reports; not formally documented by Apple.
- **Claim: There are also newer regressions (iOS 26 era, mid-2026): `eventDidReachThreshold` firing intermittently even at 0 minutes usage, or firing immediately; reported in FB since iOS 26 beta 1 (June 2025) and unaddressed ~10 months later per developer posts.** Sources: [thread 808470](https://developer.apple.com/forums/thread/808470), [thread 820956](https://origin-devforums.apple.com/forums/thread/820956). Confidence: multiple recent forum reports; version-dependent and evolving — verify against the current iOS point release.

## 6. DeviceActivityReport / DeviceActivityReportExtension (brief)

- **Claim: Usage-report UI is a separate extension (`DeviceActivityReportExtension`, point `com.apple.deviceactivityui.report-extension`) that renders SwiftUI inside a host-embedded `DeviceActivityReport` view; the extension is heavily sandboxed — no network, no shared containers/App Group writes, no NotificationCenter to the host — by design so the host app can never read the raw usage data.** Sources: [DeviceActivityReport doc](https://developer.apple.com/documentation/deviceactivity/deviceactivityreport), [DeviceActivityReportExtension doc](https://developer.apple.com/documentation/deviceactivity/deviceactivityreportextension), [WWDC22 "What's new in Screen Time API"](https://developer.apple.com/videos/play/wwdc2022/110336/), [Manish Yadav Medium](https://medium.com/@manishdevstudio/youre-absolutely-right-the-device-activity-report-extension-is-heavily-sandboxed-and-cannot-read-14fe757296dc), [matteing.com "A curious way to grab Screen Time data"](https://matteing.com/writing/a-curious-way-to-grab-screen-time-data-on-ios) (documents that exfiltration attempts fail / require hacks). Confidence: Apple official design (WWDC) + multiple corroborations.
- **Claim: iOS 17/18 didn't change the exfiltration model but brought chronic rendering problems: blank views on first load, multi-second lag, weekly/monthly filters returning blank ~80% in release builds, iOS 18.2 "heavy delay" regression.** Sources: [thread 726504](https://developer.apple.com/forums/thread/726504), [thread 728219](https://developer.apple.com/forums/thread/728219), [thread 750698](https://origin-devforums.apple.com/forums/thread/750698), [thread 767738 (iOS 18.2 regression)](https://developer.apple.com/forums/thread/767738). Confidence: multiple forum reports; version-dependent.

## 7. Debugging pain

- **Claim: `print()` output from the monitor extension is not visible in Xcode's console; use `os_log`/`Logger(subsystem:)` and watch Console.app filtered by your subsystem or by the `deviceactivityd` process.** Sources: [pedroesli.com tutorial](http://pedroesli.com/2023-11-13-screen-time-api/), [thread 724243](https://developer.apple.com/forums/thread/724243), [John Baker Medium (Shield config, same toolchain)](https://medium.com/@B4k3R/creating-a-screentime-shieldconfigurationdatasource-for-ios-familycontrols-api-5ca1079d3188). Confidence: multiple developer reports; standard extension behavior.
- **Claim: You can attach the debugger via Xcode Debug > Attach to Process once the extension process appears, but since the system spawns it on its own schedule this is hit-or-miss; most developers debug via logs and local notifications fired from callbacks.** Sources: same tutorials + [thread 746416](https://developer.apple.com/forums/thread/746416). Confidence: multiple reports.
- **Claim: End-to-end testing requires a physical device (see Simulator claim in §5) and real elapsed time — you cannot fast-forward usage accumulation, and with the 15-minute minimum interval, iteration loops are ≥15 min for schedule-boundary logic.** Sources: [letvar Medium part 3](https://letvar.medium.com/time-after-screen-time-part-3-the-device-activity-monitor-extension-284da931391b), forum threads above. Confidence: multiple reports.

### Cross-cutting caveats
- The load-bearing numbers (15 min minimum, 1 week maximum, 20 activities, 6 MB) are all **community-established, not present in Apple's current doc prose** — only the corresponding error cases (`intervalTooShort`, `intervalTooLong`, `excessiveActivities`) are officially documented. They've been stable since ~2021-2023 but could change without doc notice.
- Reliability behavior is strongly iOS-version-dependent: iOS 16 comparatively solid, iOS 17.4-17.5 introduced launch/batching failures, iOS 18 added the re-`startMonitoring` regression, iOS 26 threads report new threshold misfires. Any claim here should be re-validated on the specific target iOS version.
