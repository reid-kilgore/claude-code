# Screen Time API Research: Falsifiable Claims (as of mid-2026)

Legend: **[Apple]** = Apple official source; **[Multi]** = multiple independent reports; **[Single]** = single/unverified source. Where I could only read a page via search-result excerpts (site returned 403 to direct fetch), I say so.

## A. Earn-back / temporary-unlock architecture

- **Claim: The canonical unlock pattern is: on task completion, main app removes tokens from `ManagedSettingsStore().shield.applications` (or clears the store), persists unlock state (token, expiry timestamp) to an App Group UserDefaults, then schedules re-shielding via `DeviceActivityCenter.startMonitoring(_:during:)` with a non-repeating schedule ending at now+N; the DeviceActivityMonitor extension re-inserts the tokens in `intervalDidEnd`.** Sources: [pedroesli.com blog "Using Screen Time API to block apps for a specified time" (Nov 2023)](http://pedroesli.com/2023-11-13-screen-time-api/) (site 403'd direct fetch; pattern confirmed via search excerpts), [Habit Doom guide](https://habitdoom.com/blog/apple-screen-time-api-guide) (403; excerpts), [Apple forums thread 820956](https://developer.apple.com/forums/thread/820956) (developer describes exactly this design), Foqos source (below). **[Multi]**
- **Claim: In-app `Timer`/`DispatchQueue.asyncAfter` is not viable for re-shielding because the main app is suspended/terminated in the background and timers die; extensions (DeviceActivityMonitor) are the only wall-clock-reliable executor.** This is implicit in every implementation found (none uses in-app timers for re-shield; all use DeviceActivity schedules), and is standard iOS background-execution behavior. Direct authoritative statement not found in one place — inferred from unanimous practice. **[Multi, inferential]**
- **Claim: Foqos (open source, github.com/awaseem/foqos) implements breaks/temporary access exactly this way**: `BreakTimerActivity` calls `appBlocker.deactivateRestrictionsForBreak(for: profile)` on start and, in the monitor extension's `intervalDidEnd` path (`TimerActivityUtil.stopTimerActivity`), "Start restrictions again since break is ended" → `appBlocker.activateRestrictions(for: profile)`; state shared via `SharedData` (App Group). Schedules built with `DeviceActivitySchedule(intervalStart:intervalEnd:repeats:false)` from midnight-anchored DateComponents; its `SoftUnblockGrantScheduler` names activities `SoftUnblockGrantTimerActivity:{profileId}|{sessionId}|{grantId}` and clamps `intervalEnd` to `max(grant.expiresAt, now+60s)`. Sources: [awaseem/foqos](https://github.com/awaseem/foqos), files `Foqos/Models/Timers/BreakTimerActivity.swift`, `Foqos/Utils/SoftUnblockGrantScheduler.swift`, `Foqos/Utils/DeviceActivityCenterUtil.swift`, `FoqosDeviceMonitor/DeviceActivityMonitorExtension.swift`. **[Verified from source code]**
- **Claim: DeviceActivity schedules have a de-facto 15-minute minimum interval; `startMonitoring` with a shorter interval throws (commonly surfaced as `DeviceActivityCenter.MonitoringError` / "tightly scheduled" error), so unlocks shorter than 15 min can't be done with a plain intervalStart→intervalEnd schedule.** Sources: [letvar Medium, "Time After (Screen) Time, part 3"](https://letvar.medium.com/time-after-screen-time-part-3-the-device-activity-monitor-extension-284da931391b) ("minimum end interval of 15 minutes from the start date"), [forums thread 750623](https://developer.apple.com/forums/thread/750623) (workaround list: "Minimum schedule interval must be at least 15 minutes — anything less won't trigger the monitor"). **Note: NOT in Apple's docs** — the [`DeviceActivitySchedule` doc](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule) and [`startMonitoring` doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:)) only say "Attempting to monitor too many activities or activities that are too tightly scheduled can cause this method to throw an error." **[Multi; undocumented by Apple]**
- **Claim: For sub-15-minute earned time, the standard workarounds are (a) a usage-based `DeviceActivityEvent` threshold of N minutes on the unlocked app(s) inside a longer schedule, re-shielding in `eventDidReachThreshold` (making it usage-based rather than wall-clock), or (b) a ≥15-min schedule whose `warningTime` fires earlier (`intervalWillEndWarning`).** Sources: Apple's own [`startMonitoring` doc](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:)) explicitly suggests "consider using the `warningTime` property"; [`DeviceActivitySchedule.warningTime`](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule) ("callbacks whenever a schedule is about to start or end, or when an event is close to reaching its threshold"); event-threshold pattern in [kingstinct/react-native-device-activity README](https://github.com/kingstinct/react-native-device-activity) (`eventName: 'minutes_reached_10', threshold: {minute:10}` + `eventWillReachThresholdWarning`). **[Multi; warningTime hint is Apple official]**
- **Claim: `includesPastActivity: false` (iOS 17.4+) is needed for correct earned-time thresholds, otherwise usage before `startMonitoring` counts toward the threshold — and even with `true`, activity is counted from the nearest round hour, a documented quirk.** Source: [Apple docs, `includesPastActivity`](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/includespastactivity) — availability iOS 17.4+/iPadOS 17.4+/Catalyst 17.4+; quote: "if your app calls startMonitoring at 1:30pm with a schedule of 1:00pm to 2:00pm, this boolean determines whether activity between 1:00pm and 1:30pm will contribute to its threshold." **[Apple]**
- **Claim: Calling `startMonitoring()` again (e.g., chaining checks) can itself trigger `intervalDidEnd` for a replaced activity, re-blocking everything mid-unlock — you must guard `intervalDidEnd` with a shared-state check ("is an unlock session still active?") before re-shielding.** Source: [Habit Doom guide](https://habitdoom.com/blog/apple-screen-time-api-guide) (403; via search excerpts — "startMonitoring() triggering intervalDidEnd as a side effect"). **[Single unverified — treat as plausible practitioner report]**
- **Claim: Non-repeating schedules far in the future are unreliable (reported unreliable beyond ~45–90 min), so long unlocks are best implemented by chaining shorter schedules (e.g., checks at 15/30/44 min) with a 1–2 min buffer past the expected expiry.** Sources: [Habit Doom](https://habitdoom.com/blog/apple-screen-time-api-guide) (403; excerpts: "schedules unreliable beyond 45 minutes", chaining pattern), corroborated in spirit by widespread `intervalDidEnd`-not-firing reports ([thread 820956](https://developer.apple.com/forums/thread/820956)). **[Single for exact numbers; Multi for general unreliability]**
- **Claim: There is a hard limit of 20 simultaneous DeviceActivity monitors (activities).** Source: [kingstinct/react-native-device-activity README](https://github.com/kingstinct/react-native-device-activity) ("There's a hard limit on 20 monitors at the same time"). Not in Apple docs. **[Single, widely repeated in RN community; undocumented]**
- **Claim: There is no API for the shield UI to unlock the app directly; `ShieldActionDelegate` buttons can only close/defer — apps must bounce the user to the main app to complete a task/intervention, and cross-process state must go through App Group UserDefaults (extensions can't share SwiftData/CoreData reliably).** Sources: [riedel.wtf, "Apple's Screen Time API has some major issues" (Sept 14, 2024)](https://riedel.wtf/state-of-the-screen-time-api-2024/) (403; via excerpts: "user wants to perform some action to unlock more time... Unfortunately, there's no API for that"), [Habit Doom](https://habitdoom.com/blog/apple-screen-time-api-guide) (App Group state). **[Multi]**
- **Claim: `intervalDidStart`/`intervalDidEnd` reliability depends on how DateComponents are built — using only hour/minute/second components for both ends is the reliable form.** Source: [letvar Medium part 3](https://letvar.medium.com/time-after-screen-time-part-3-the-device-activity-monitor-extension-284da931391b). **[Single practitioner report]**

## B. How Opal / Jomo / one sec do it (public info)

- **Claim: Opal originally did NOT use the Screen Time API — its early "Screen Time Framework" blog describes an on-device VPN that measured usage and blocked app network connections ("iOS Screen Time is not available as a public API, so we built our own way").** Source: [Building Opal's Screen Time Framework](https://opalapp.com/blog/opals-screen-time-framework) (403 to direct fetch; via search excerpts). Version-dependence: predates FamilyControls maturity (blog is from Opal's early era, ~2020–21). **[Single/company blog, historical]**
- **Claim: Current Opal uses Apple's Screen Time API (FamilyControls permission) for blocking; "breaks" were renamed "Unblock", available from the app, with configurable friction levels up to a "hardcore mode" (Opal Pro) where limits can't be reset — i.e., break policy is enforced by Opal's own logic on top of shield add/remove, not by any special Apple API.** Sources: [Opal FAQ: why Screen Time API permissions](https://opalapp.com/help/why-do-you-need-to-grant-screen-time-api-access) (403; excerpt), [Opal FAQ: Time Limits](https://opalapp.com/help/what-are-time-limits). **[Company docs; Multi for "uses Screen Time API"]**
- **Claim: Jomo publicly describes earn-back mechanics — "Routines" complete habits to unlock apps or "earn time progressively," plus limited unlocks per day and exercise-gated unlocking — all built on the Screen Time API ("Jomo uses the secure Screen Time API provided by Apple").** Sources: [Jomo App Store listing](https://apps.apple.com/us/app/jomo-screen-time-blocker/id1609960918), [jomo.so](https://jomo.so/). No engineering blog found describing internals. **[Company marketing; no independent technical detail]**
- **Claim: one sec (Frederik Riedel) intercepts app opens and gates re-entry behind an intervention (breathing exercise); its developer's Sept 2024 post is the best public engineering account of the API's problems: iOS "randomly changes tokens," giving the shield extension tokens the app has never seen (so it can't pick the right UI or find which store blocks the app, since old tokens linger in the store), and shield-context identification is impossible — problems he says were confirmed by ScreenZen, Jomo, and Opal developers.** Sources: [riedel.wtf state-of-the-screen-time-api-2024](https://riedel.wtf/state-of-the-screen-time-api-2024/) (published 2024-09-14; 403 to fetch, content via multiple search excerpts), [one sec Screen Time API issues help page](https://tutorials.one-sec.app/en/articles/3036354) (403), [RevenueCat interview](https://www.revenuecat.com/blog/growth/frederik-riedel-expected-12-his-app-cut-screen-time-by-57/). **[Multi]**
- **Claim: No Opal/Jomo/one sec engineering blog publishes the exact re-shielding scheduling mechanism; the only fully-inspectable implementations are open source (Foqos; kingstinct/react-native-device-activity; Klouckup/foqos fork).** **[Assessment from this research — absence of evidence, moderate confidence]**

## C. iOS 17/18/26/27 + WWDC 2024/2025/2026

This touches FamilyControls only indirectly (Family Sharing / parental-consent plumbing).** Sources: [Apple developer news "New requirements for apps available in Texas"](https://developer.apple.com/news/?id=btkirlj8), [Apple news update](https://developer.apple.com/news/?id=2ezb6jhj), [MoFo analysis](https://www.mofo.com/resources/insights/251111-texas-targets-app-stores-with-new-accountability-law), [Wiley alert](https://www.wiley.law/alert-Key-Developments-With-State-App-Store-Accountability-Acts-as-Texas-Act-Takes-Effect). **[Apple + Multi]**

## D. Known bugs 2024–2026 (Apple Developer Forums, dated)

- **Claim: `intervalDidEnd` not invoked for non-repeating timed-unlock schedules on iOS 26.3.1 (iPhone 17 Pro, Xcode 26.4) — app never re-locks; extension apparently never launched; no Apple fix, only "file Feedback" advice.** Source: [thread 820956](https://developer.apple.com/forums/thread/820956), created Mar 2026, last post Apr 2026. **[Single thread, recent; matches long pattern]**
- **Claim: "Screen Time API is completely UNRELIABLE" (Apr 2024, iOS 17.4): `DeviceActivityReport` not rendering, `intervalDidStart` frequently not firing; reply warns iOS 17.5 made it worse "even for apps that had been working"; workarounds posted include the 15-min minimum and doing shielding work in `intervalDidEnd`; poster notes Opal/Jomo don't seem affected, implying undocumented tricks.** Source: [thread 750623](https://developer.apple.com/forums/thread/750623), Apr–May 2024, no Apple reply. **[Multi participants]**
- **Claim: Random non-delivery of DeviceActivityMonitor callbacks in production (unreproducible in dev) reported Jan 2025; Apple Frameworks Engineer replied (Feb 2025) only that processes are killed on memory/idle and "you shouldn't need to do anything special" — no acknowledgment or fix.** Source: [thread 773228](https://developer.apple.com/forums/thread/773228). **[Multi reports; Apple reply on record]**
- **Claim: `eventDidReachThreshold` bugs across versions: fires immediately (seconds, not at threshold) on iOS 26.x betas including iOS 26.2 (23C55); fires multiple times; fires with 0 recorded usage; or extension fails to launch for minutes/hours. Common user-level workaround: revoke and re-grant Screen Time permission, which "holds for about two weeks."** Sources: [thread 811305 (iOS 26.2)](https://developer.apple.com/forums/thread/811305), [thread 737741](https://developer.apple.com/forums/thread/737741), [thread 763542 (overcounting)](https://developer.apple.com/forums/thread/763542). **[Multi]**
- **Claim: `AuthorizationCenter.authorizationStatus` is unreliable: revoking Screen Time access in Settings leaves status `.approved` while the app runs; after relaunch it reads `.notDetermined` instead of `.denied`; tapping "Don't Allow" leaves `.notDetermined`. Reported on iOS 17.4 and still on iOS 18.3.1 (thread created ~Feb 2024, "Family Controls: authorizationStatus... completely broken").** Source: [thread 747915](https://developer.apple.com/forums/thread/747915), [AuthorizationCenter docs](https://developer.apple.com/documentation/familycontrols/authorizationcenter). **[Multi]**
- **Claim: `requestAuthorization` failures "The operation couldn't be completed. (FamilyControls.FamilyControlsError error N)": error 2 = invalidAccountType (expected on non-child account with `.child` request); error 3 = internal error, notoriously appearing on Simulator and sometimes on device, where the nuclear fix reported is wiping the device; error-casting bugs for codes 4/5/7 fixed in iOS 16.4.** Sources: [thread 684355](https://developer.apple.com/forums/thread/684355), [thread 708050](https://developer.apple.com/forums/thread/708050), [thread 735277](https://forums.developer.apple.com/forums/thread/735277). **[Multi]**
- **Claim: Token instability is real and unfixed as of late 2024: iOS occasionally re-issues ApplicationTokens; the shield extension then receives tokens the app has never stored, while stale tokens remain in the ManagedSettingsStore — breaking any token→metadata mapping (one sec, confirmed by ScreenZen/Jomo/Opal devs).** Source: [riedel.wtf, 2024-09-14](https://riedel.wtf/state-of-the-screen-time-api-2024/) (via excerpts). **[Multi via author's cross-app confirmation; primary page not directly fetchable here]**
- **Claim: Shield rendering gaps: category-shielding misses some system apps (`applicationCategories = .all()` doesn't shield system apps); compact Live Activities in Dynamic Island escape shielding; ShieldConfiguration customization sometimes not applied (thread "Shield Customisation Not Applying"); App Switcher rendering artifact with custom `backgroundColor` shields on iOS 18/26.** Sources: [thread 725168](https://developer.apple.com/forums/thread/725168), [thread 724419](https://developer.apple.com/forums/thread/724419), [Managed Settings forum tag](https://developer.apple.com/forums/tags/managed-settings). **[Multi]**
- **Claim: iOS 18.4/18.5/26 beta regression: `FamilyActivityPicker` inside a sheet dismisses the presenting sheet when "Done" is tapped.** Source: Family Controls forum tag reports ([forums tag family-controls](https://developer.apple.com/forums/tags/family-controls)). **[Multi reports, version-specific 18.4–26b2]**
- **Claim: Callbacks work while attached to Xcode debugger but stop firing when the device is disconnected / release builds — a recurring 2024 report (e.g., FB13556935 filed with sysdiagnose).** Source: [thread 745035](https://developer.apple.com/forums/thread/745035), [thread 746416](https://developer.apple.com/forums/thread/746416). **[Multi]**
- **Claim: Reboot-persistence: DeviceActivity schedules are supposed to survive reboot, but multiple 2024–2026 threads report monitors going dead until re-registration; no Apple confirmation.** Sources: [device-activity forum tag](https://developer.apple.com/forums/tags/device-activity), [thread 805859 (2025, "Device Activity monitor extension Not working")](https://developer.apple.com/forums/thread/805859). **[Multi, weakly specified — I did not find one canonical "after reboot" thread; flag as lower confidence]**

## E. Testing constraints

- **Claim: The Screen Time API is effectively unusable on the iOS Simulator: `FamilyActivityPicker` doesn't work, shields don't render, DeviceActivity monitoring doesn't track, and `requestAuthorization` commonly fails with FamilyControlsError Code=3 even on child accounts — despite one Apple engineer forum statement that requesting authorization on Simulator "is supported." Physical device is required for any meaningful test.** Sources: [thread 684355](https://developer.apple.com/forums/thread/684355) (Apple engineer comment + Code=3 reports), [thread 685126](https://developer.apple.com/forums/thread/685126?page=2), [kingstinct README](https://github.com/kingstinct/react-native-device-activity), [Julius Brussee Medium guide](https://medium.com/@juliusbrussee/a-developers-guide-to-apple-s-screen-time-apis-familycontrols-managedsettings-deviceactivity-e660147367d7). **[Multi; the exact failure mode (auth succeeds vs errors) varies by Xcode/iOS version — version-dependent]**
- **Claim: `com.apple.developer.family-controls` works for local development (Xcode → device) without Apple approval, but ANY distribution — including TestFlight (internal or external) — requires per-bundle-ID approval of the distribution entitlement via Apple's request form; Apple DTS (Quinn "The Eskimo!", Aug 2022) stated this explicitly, and it remains the rule in the [entitlement doc](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.family-controls).** Source: [thread 712870](https://developer.apple.com/forums/thread/712870). **[Apple official]** (Reports that "you can TestFlight with dev entitlement" appear to stem from confusion — the build uploads but Family Controls silently fails at runtime.)
- **Claim: You must request the distribution entitlement separately for the main app AND every extension bundle ID (DeviceActivityMonitor, ShieldConfiguration, ShieldAction, DeviceActivityReport); until all are approved "you are stuck with local development builds in Xcode"; approval turnaround is unpredictable (days to months per community reports).** Sources: [thread 712870, Apr 2024 comment](https://developer.apple.com/forums/thread/712870), [kingstinct README](https://github.com/kingstinct/react-native-device-activity) ("Four bundle identifiers per base app require separate approval requests"). **[Multi; turnaround-time claim Single/anecdotal]**
- **Claim: A common TestFlight failure after approval is misconfigured signing, not Apple policy — e.g., the entitlement present in the Debug but not Release build configuration (Nov 2025 thread, self-resolved), or provisioning profiles not regenerated after entitlement grant.** Source: [thread 806285](https://developer.apple.com/forums/thread/806285). **[Multi]**
- **Claim: TestFlight external testing additionally requires Beta App Review of the first build of each version — so an unapproved-entitlement build can also stall there.** Source: [Apple: Invite external testers](https://developer.apple.com/help/app-store-connect/test-a-beta-version/invite-external-testers/). **[Apple]**
- **Claim: Practical device-testing gotchas: the 15-minute minimum makes iteration slow (each wall-clock test ≥15 min unless using event thresholds); extension callbacks behave differently attached vs detached from the debugger; recommended diagnostics include disabling Low Power Mode, rebooting, and checking free storage ("the Screen Time APIs are known to be very finnicky").** Sources: [letvar part 3](https://letvar.medium.com/time-after-screen-time-part-3-the-device-activity-monitor-extension-284da931391b), [kingstinct README troubleshooting](https://github.com/kingstinct/react-native-device-activity), [thread 745035](https://developer.apple.com/forums/thread/745035). **[Multi]**

## Caveats on this research

- Direct fetches of riedel.wtf, habitdoom.com, opalapp.com, one-sec tutorials, and macrumors.com returned HTTP 403 through this environment's proxy; claims from those sites came from search-result excerpts and should be spot-checked at the URLs given. Foqos claims were verified against actual source code via GitHub; Apple doc claims via the developer.apple.com JSON documentation endpoints; forum claims via direct fetches of the threads (820956, 750623, 773228, 712870, 806285 fetched in full).
- The strongest single fault line for the earn-back architecture in mid-2026 is that the reliable-by-design mechanism (`intervalDidEnd` re-shield) is itself the subject of active iOS 26.x bug reports (thread 820956) — so production apps belt-and-suspender it: monitor-extension re-shield + re-check on main-app foreground (`scenePhase`) + expiry timestamps in App Group state, never a bare flag.
