> Research brief produced by a web-research agent on 2026-07-09 for the Flashlock project.
> Topic: Shield extensions & app-extension IPC. Claims are cited inline; confidence flags are the agent's own.

# Research Findings: ManagedSettingsUI Shield Extensions (as of mid-2026)

**HEADLINE UPDATE that invalidates prior assumptions:** Apple shipped `ShieldActionResponse.openParentalControlsApp` in **iOS 26.5** — there is now an official API to open the containing app from a ShieldAction extension. Apple also added `secondaryButtonSubmenuItems` (up to 3 custom submenu actions) in **iOS 26.4**. Details below.

---

## 1. ShieldConfiguration extension (customization surface)

- **Claim:** The full customizable surface of `ShieldConfiguration` is exactly: `backgroundBlurStyle: UIBlurEffect.Style?`, `backgroundColor: UIColor?`, `icon: UIImage?`, `title: ShieldConfiguration.Label?`, `subtitle: ShieldConfiguration.Label?`, `primaryButtonLabel: ShieldConfiguration.Label?`, `primaryButtonBackgroundColor: UIColor?`, `secondaryButtonLabel: ShieldConfiguration.Label?`, and (new) `secondaryButtonSubmenuItems: [String]?`. `ShieldConfiguration.Label` carries text + color only.
  Source: [ShieldConfiguration docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfiguration), [initializer docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfiguration/init(backgroundblurstyle:backgroundcolor:icon:title:subtitle:primarybuttonlabel:primarybuttonbackgroundcolor:secondarybuttonlabel:)). **Apple official.**
- **Claim:** `secondaryButtonSubmenuItems` is new in **iOS 26.4 / iPadOS 26.4 / Mac Catalyst 26.4**; max 3 items; system auto-adds a Cancel button; items map to new `ShieldAction` cases `.firstSecondarySubmenuItemPressed` / `.secondSecondarySubmenuItemPressed` / `.thirdSecondarySubmenuItemPressed`; nil/empty array falls back to plain `.secondaryButtonPressed`.
  Source: [secondaryButtonSubmenuItems docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfiguration/secondarybuttonsubmenuitems). **Apple official.** Version-dependent: only on 26.4+.
- **Claim:** Layout is fixed by Apple — you cannot supply arbitrary views, images beyond the single center `icon`, reposition elements, or remove Apple's shield chrome. The system provides a default appearance for any nil property and for any `ShieldConfigurationDataSource` method you don't override — and **also when your configuration returns too slowly** (i.e., a slow extension silently yields the default shield).
  Source: [ShieldConfigurationDataSource docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfigurationdatasource) ("expected to return an appropriate configuration as quickly as possible"; "system provides a default appearance for any methods... or if configuration returns too slowly"). **Apple official** (fixed layout is by omission — no view API exists — plus universal community consensus).
- **Claim:** `secondaryButtonLabel` = nil hides the secondary button entirely; `primaryButtonLabel` = nil gets a system default ("Close"/"OK") — the primary button cannot be removed.
  Source: [Medium — John Baker ShieldConfigurationDataSource guide](https://medium.com/@B4k3R/creating-a-screentime-shieldconfigurationdatasource-for-ios-familycontrols-api-5ca1079d3188); Apple init docs. **Apple official + tutorial corroboration.**
- **Claim:** Extension point identifier for the config extension is `com.apple.ManagedSettingsUI.shield-configuration-service` (NSExtensionPointIdentifier), principal class = your `ShieldConfigurationDataSource` subclass. The **action** extension's identifier is `com.apple.ManagedSettings.shield-action-service` — note **no "UI"**; using `com.apple.ManagedSettingsUI.shield-action-service` causes App Store upload rejection ("invalid Info.plist value"), confirmed by an Apple DTS engineer in Feb 2026.
  Source: [Forum thread 814945](https://developer.apple.com/forums/thread/814945) (DTS reply), [thread 729963](https://developer.apple.com/forums/thread/729963). **Apple DTS official.**
- **Claim (memory limit):** No Apple-published number exists for shield extensions. The **DeviceActivityMonitor** extension has a widely-reported hard ~**6 MB** jetsam limit (Frederik Riedel of one sec: "the 6 MB limit has become a critical bottleneck... frequently crashing due to memory pressure"). Shield extensions are believed similarly constrained, but I found **no specific published jetsam figure for the ShieldConfiguration/ShieldAction extensions** — flag as uncertain; treat "keep it tiny" as the engineering rule.
  Source: [Forum thread 745035](https://developer.apple.com/forums/thread/745035), [Device Activity forum tag](https://developer.apple.com/forums/tags/device-activity), [Apple jetsam docs](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports). **Multiple forum reports for DAM's 6 MB; single/unverified for shield extensions specifically.**
- **Claim (dynamic config):** The standard pattern for dynamic shield text is: main app writes to an App Group `UserDefaults(suiteName:)`; the extension reads it inside `configuration(shielding:)` on each invocation. Confirmed workable by an Apple Frameworks Engineer: "Even though Shield Configuration extensions are heavily sandboxed, you should still be able to read data from your app group's container."
  Source: [Forum thread 716698](https://developer.apple.com/forums/thread/716698) (accepted, Apple engineer), [John Baker App Group guide](https://medium.com/@B4k3R/setting-up-your-appgroup-to-share-data-between-app-extensions-in-ios-43c7c642c4c7). **Apple engineer + multiple reports.**
- **Claim (invocation/caching gotcha):** The config extension is invoked when the shield is (re)displayed — i.e., when the user opens a shielded app — **not** when you mutate `ManagedSettingsStore.shield.applications` while the target app is foregrounded. Known bug: if the shielded app is already open/foreground when shields change, iOS recycles a **stale** ShieldConfiguration instead of re-querying (reproduced against OffScreen; time-limit text goes stale).
  Source: [Forum thread 717269 "ShieldConfiguration not updating"](https://developer.apple.com/forums/thread/717269). **Multiple forum reports; Apple has not documented refresh timing.**
- **Claim (default-shield-shown gotchas):** Reported causes and fixes for "my custom shield never appears, default 'Restricted' shield shows": (a) extension target's **minimum deployment target must match** the app's (most-cited fix); (b) extension must be a real embedded appex target, not just a class in the app; (c) wrong NSExtensionPointIdentifier; (d) **PDF icon assets can break the whole configuration — switching the icon to PNG made the custom shield appear** (Aug 2024 report); (e) clean build / delete app / **device restart** sometimes required; (f) compile the extension target before running the app.
  Source: [thread 725168](https://developer.apple.com/forums/thread/725168), [thread 729963](https://developer.apple.com/forums/thread/729963). **Multiple forum reports; no Apple confirmation of root causes.**
- **Claim (icon/assets):** `icon` is a plain `UIImage`; no documented size constraint — the system renders it at a fixed frame in the center. `UIImage(named:)` works in the extension **only if the asset catalog is included in the extension target's membership/Build Phases** (or a shared catalog assigned to both targets). Known bug report: the icon does not re-render on light/dark appearance change until shields are re-applied (Apple engineer asked for a Feedback, i.e., treated as bug).
  Source: [thread 734995](https://developer.apple.com/forums/thread/734995), [thread 720771](https://developer.apple.com/forums/thread/720771). **Multiple forum reports; icon size limits: no evidence found (uncertain).**
- **Claim (localization):** No special API; the extension is a normal bundle, so `Localizable.strings`/String Catalogs in the **extension target** work and follow device locale; dynamic per-user language must be passed via App Group defaults. (This is inferred from standard extension bundle behavior plus the App Group pattern above — I found no authoritative page specifically on shield localization.) **Inference / weak sourcing — flag as unverified.**

## 2. ShieldAction extension & opening the containing app

- **Claim:** `ShieldActionDelegate` exposes three overloads of `handle(action:for:completionHandler:)` for `ApplicationToken`, `WebDomainToken`, `ActivityCategoryToken`. The system deliberately passes only opaque tokens (no display names) "to preserve the Family Sharing group's privacy."
  Source: [ShieldActionDelegate docs](https://developer.apple.com/documentation/managedsettings/shieldactiondelegate). **Apple official.**
- **Claim:** `ShieldActionResponse` cases as of iOS 26.5: `.none` ("system doesn't need to take any additional action"), `.close` ("close the current application or web browser"), `.defer` ("defer a response"), and **`.openParentalControlsApp`** ("open your parental controls app that is responsible for shielding the application or web browser") — the latter **introduced in iOS 26.5 / iPadOS 26.5 / Mac Catalyst 26.5**, not beta, not deprecated.
  Source: [ShieldActionResponse docs](https://developer.apple.com/documentation/managedsettings/shieldactionresponse), [openParentalControlsApp availability page](https://developer.apple.com/documentation/managedsettings/shieldactionresponse/openparentalcontrolsapp). **Apple official.** Corroboration: one sec's blog states "As of iOS 26.5 or newer, users will no longer have to do the notification dance" for re-interventions ([one-sec.app blog](https://one-sec.app/blog/lock-screen-time-permission/), [one sec tutorials](https://tutorials.one-sec.app/screen-time-api-issues)). **Strong. Highly version-dependent: on iOS ≤26.4 the old reality below still holds.**
- **Claim (pre-26.5 state, still true for older OSes):** There was **no supported way** to open the main app from the extension. Apple Frameworks Engineer (Nov 2022, reiterated Oct 2024 and Jan 2025): "There's no supported way for your extension to open your main app with the APIs currently available... file an enhancement request." `UIApplication.shared` is unavailable, `NSExtensionContext`/`extensionContext.open(_:)` is unavailable in this extension type, SwiftUI `openURL` fails silently, and a responder-chain selector trick broke on iOS 18+. Apps caught using private `LSApplicationWorkspace` got App Store rejections under guideline 2.5.1 (report from May 2026); apps like AppLocker/Wellspent were long suspected of using the private API.
  Source: [thread 719905](https://developer.apple.com/forums/thread/719905), [thread 766644](https://developer.apple.com/forums/thread/766644). **Apple engineer statements + many corroborating reports.**
- **Claim (notification workaround):** The historically Apple-compliant workaround is: return `.close`, and have the extension schedule a **local notification** via `UNUserNotificationCenter` (usable from the ShieldAction extension per developer reports) with a deep link; tapping it opens the main app — costs ~1 second and an extra tap. Described in a May 2026 Feedback (FB22696417) as "the only Apple-compliant mechanism." one sec called this the "notification dance," now obsolete on 26.5+. Caveats reported: notification permission required; deliveries can be delayed by Apple Intelligence summaries or suppressed by Focus.
  Source: [thread 719905](https://developer.apple.com/forums/thread/719905), [one sec tutorials/blog](https://tutorials.one-sec.app/screen-time-api-issues). **Multiple forum reports; no Apple doc blesses or forbids UNUserNotificationCenter in this extension — moderately confident it works, flag as not officially documented.**
- **Claim (other workarounds):** Instructing the user to manually open the app after `.close` is common (Foqos returns `.close` on every path after mutating shared state — see its [ShieldActionExtension.swift](https://github.com/awaseem/foqos/blob/main/FoqosShieldAction/ShieldActionExtension.swift), which issues a "soft unblock grant" via shared app-group state, then `.close`). Darwin notifications can signal the main app **only if it's already running**. **Verified from Foqos source (single OSS project) + Darwin semantics below.**

## 3. `.defer` and `.none` semantics

- **Claim:** `.defer` causes the system to **re-invoke your ShieldConfiguration extension** and redraw the shield ("makes iOS ask your ShieldConfiguration extension for a new shield that properly demonstrates this new state" — Apple Frameworks Engineer). The shield stays up (with a brief spinner on the pressed button per community reports) until the fresh configuration renders. Critical limitation: the config callback receives **no context** about why it's being called — you must round-trip state through the App Group to render a different "post-action" shield.
  Source: [thread 716698](https://developer.apple.com/forums/thread/716698) (Apple engineer), [ShieldActionResponse.defer docs](https://developer.apple.com/documentation/managedsettings/shieldactionresponse/defer). **Apple engineer + official docs.**
- **Claim:** `.none` leaves the shield exactly as-is — no dismissal, no reconfiguration; use it when the button should appear to "do nothing" (or after you've already unshielded via `ManagedSettingsStore` in the handler). Note: if you clear the shield in the handler and return `.close`, the target app closes anyway; reports of the shield not hiding promptly after store mutation exist ([thread 807934](https://developer.apple.com/forums/thread/807934)). **Apple official for the definition; behavior nuances = forum reports.**

## 4. App <-> extension communication

- **Claim:** There is no direct IPC channel to shield extensions; supported sharing is **App Groups**: shared `UserDefaults(suiteName:)`, shared container files, and Core Data/SQLite in the group container ("If the extension can access a file in an App Group container, it should be able to access a Core Data store at the same place" — but watch multi-process SQLite locking and the tiny memory budget; a report of Core Data queries misbehaving in the extension: [thread 766639](https://developer.apple.com/forums/thread/766639)).
  Source: [thread 716698](https://developer.apple.com/forums/thread/716698), [John Baker App Group guide](https://medium.com/@B4k3R/setting-up-your-appgroup-to-share-data-between-app-extensions-in-ios-43c7c642c4c7). **Apple engineer + multiple reports.**
- **Claim:** `UserDefaults.didChangeNotification` does **NOT** fire for changes made by another process — Apple's exact words: "If a different process changes your app's settings, the system doesn't generate this notification. To detect changes made by another process, register a key-value observer on the UserDefaults object. Key-value observing reports all updates to setting values, regardless of which process made the change."
  Source: [UserDefaults.didChangeNotification docs](https://developer.apple.com/documentation/foundation/userdefaults/didchangenotification). **Apple official.** However: real-world reports that cross-process KVO on shared-suite defaults is flaky on iOS (TCA `@Shared`/appStorage issues [#3439](https://github.com/pointfreeco/swift-composable-architecture/issues/3439), [discussion #3459](https://github.com/pointfreeco/swift-composable-architecture/discussions/3459); keys containing "." break keyPath observation). **Apple says it works; community reports mixed — flag disagreement.**
- **Claim:** `CFNotificationCenterGetDarwinNotifyCenter` delivers system-wide notifications between app and extensions, but carries **no payload** (userInfo/object are ignored) and is delivered only to processes that are alive and registered at post time — it cannot launch or wake a suspended main app. Pattern: post Darwin notification + read details from App Group storage.
  Source: [Apple CFNotificationCenter docs](https://developer.apple.com/documentation/corefoundation/cfnotificationcentergetdarwinnotifycenter()), [Nonstrict blog](https://nonstrict.eu/blog/2023/darwin-notifications-app-extensions/), [OhMySwift guide](https://ohmyswift.com/blog/2024/08/27/send-data-between-ios-apps-and-extensions-using-darwin-notifications/), [Apple Darwin Notification Concepts (archive)](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/MacOSXNotifcationOv/DarwinNotificationConcepts/DarwinNotificationConcepts.html). **Apple official (no payload) + multiple blogs (delivery-while-running).**
- **Claim:** Keychain sharing via keychain access groups works between an app and its extensions (standard mechanism, applies to shield extensions as normal appexes) — but given the ~6 MB-class memory ceilings and the no-network sandbox, App Group defaults remain the dominant pattern in shipped Screen Time apps.
  Source: [Apple — Sharing access to keychain items](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps). **Apple official for the mechanism; its use inside shield extensions specifically = inference, not separately verified.**

## 5. Sandbox, network, entitlements

- **Claim:** The ShieldConfiguration extension **cannot make network requests** — Apple's docs state it verbatim: "To protect the Family Sharing group's privacy, the Shield Configuration extension runs in a sandbox. This sandbox prevents your extension from making network requests or moving sensitive content outside the extension's address space."
  Source: [ShieldConfigurationDataSource docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfigurationdatasource). **Apple official.** The ShieldAction delegate page does not carry the identical sentence, but the same privacy/token design applies and community reports treat both as network-restricted; DeviceActivityMonitor extensions are likewise reported unable to network. **For ShieldAction specifically: strong community consensus, not verbatim in docs — flag.**
- **Claim:** All Screen Time extension targets (ShieldConfiguration, ShieldAction, DeviceActivityMonitor) must carry the **Family Controls capability/entitlement** (`com.apple.developer.family-controls`) in addition to the main app; missing it on the extension target is a classic cause of the extension never being invoked. The distribution entitlement for App Store builds requires Apple's approval request form.
  Source: tutorial chain ([pedroesli Screen Time API guide](http://pedroesli.com/2023-11-13-screen-time-api/), [John Baker Medium](https://medium.com/@B4k3R/creating-a-screentime-shieldconfigurationdatasource-for-ios-familycontrols-api-5ca1079d3188), [ScreenBreak demo](https://github.com/christianp-622/ScreenBreak), Foqos entitlement files), forum troubleshooting threads. **Multiple tutorial/forum reports; Apple docs imply but don't state it in one sentence — flag as strongly-believed, not verbatim-official.**
- **Claim:** Execution constraints: the config extension must return synchronously-fast (slow = default shield, no error); a fresh `ShieldConfigurationDataSource` instance may be created per query, so in-memory state doesn't persist across invocations ("you get a new instance every time").
  Source: [thread 716698](https://developer.apple.com/forums/thread/716698), [ShieldConfigurationDataSource docs](https://developer.apple.com/documentation/managedsettingsui/shieldconfigurationdatasource). **Apple official + Apple-engineer-acknowledged thread.**

## Key version-dependence summary

| Capability | iOS ≤17 | iOS 18–26.3 | iOS 26.4 | iOS 26.5+ |
|---|---|---|---|---|
| Open app from ShieldAction | No (responder-chain hack worked ≤17) | No (hack dead; notification dance) | No | **Yes — `.openParentalControlsApp`** |
| Secondary-button submenu (3 items) | No | No | **Yes** | Yes |
| Shield customization surface | 8 params, fixed layout | same | same + submenu | same |

**Gaps/uncertainties I could not resolve:** exact jetsam limit for the two shield extension types (only DAM's 6 MB is well-attested); any documented icon pixel-size constraint (none found; PDF-vs-PNG failure is the only concrete asset gotcha); whether `.openParentalControlsApp` requires any new entitlement or Info.plist key beyond existing setup (Apple's doc page shows none); pedroesli.com and one-sec.app blocked direct fetching (403), so their claims are cited via search-index snippets.
