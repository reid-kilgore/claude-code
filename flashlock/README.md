# Flashlock

An iOS app that couples a screen-time blocker (à la Brick / Focus Friend) with an
Anki-style spaced-repetition flashcard app: when your selected apps hit their
daily limit they lock, and the only way to earn more time is to **clear a pile
of flashcards** — missed cards go back in the pile until you get them right,
and every pile includes recall cards (multiple choice or typed) you can't mash
through.

## Status

- **FlashlockCore: implemented and verified.** The FSRS-6 scheduler is a
  line-for-line port of the reference implementation (py-fsrs 6.3.1) and is
  verified two independent ways:
  1. **Golden vectors** — review sequences generated by the reference package
     are replayed in the Swift test suite
     (`Tests/FlashlockCoreTests/Resources/fsrs_golden_vectors.json`).
  2. **Cross-implementation fuzzing** — `scripts/fsrs_port_check.py` runs a
     transliteration of the Swift logic against py-fsrs over 4,000 random
     review sequences (~30k reviews): zero divergence in state, stability,
     difficulty, or due dates.
- **iOS app layer: complete skeleton** (SwiftUI app, DeviceActivityMonitor /
  ShieldConfiguration / ShieldAction extensions, XcodeGen project). Written
  against the researched API surface but **not yet compiled** — this
  environment has no Apple toolchain. Expect a short fix-up pass in Xcode.
- **Research: done and captured** in `docs/research/` with citations and
  confidence flags.

## Running the tests (needs a Swift toolchain — any Mac, or Linux with Swift 6)

```sh
cd flashlock/FlashlockCore
swift test
```

To re-verify the scheduler against the reference implementation:

```sh
pip install fsrs==6.3.1
python3 flashlock/scripts/fsrs_port_check.py     # fuzz equivalence check
python3 flashlock/scripts/gen_fsrs_vectors.py    # regenerate golden vectors (stdout)
```

## Getting your Anki cards in (and keeping them in sync)

```sh
# In Anki: File → Export → .apkg, with "Support older Anki versions" CHECKED
python3 flashlock/scripts/apkg_to_flashlock.py MyDeck.apkg -o mydeck.flashlock.json
# AirDrop / Files the JSON to the phone, then in Flashlock: Decks → Import deck…
```

Re-running the script and re-importing is the sync: cards match on Anki's
stable note guid, so text edits update in place, new notes are added,
**scheduling state is never touched, and nothing is ever deleted**. Front/back
come from the note's first two fields (`--front/--back` to override), HTML and
media references are stripped, cloze notes are skipped, and `--mode
multipleChoice|typed` marks the whole import as recall cards for the gate.

## Building the app

See `Flashlock/README.md`. Short version: `brew install xcodegen`,
`xcodegen generate`, open in Xcode, set your team, run on a **physical device**
(the Screen Time APIs do not work in the Simulator).

## The five facts that shaped the design

(Full citations in `docs/research/`.)

1. **Distribution is gated by Apple.** Dev builds work immediately, but
   TestFlight/App Store require Apple to grant the Family Controls entitlement
   for the app *and each of the three extensions*, via a request form with
   days-to-weeks silent turnaround. File early.
2. **The shield can't run your code — and until iOS 26.5 couldn't even open
   your app.** Shield buttons historically could only close/defer (hence the
   local-notification hop); iOS 26.5 finally added
   `ShieldActionResponse.openParentalControlsApp`. We support both paths.
3. **Extensions are headless and tiny (~6 MB).** All cross-process state goes
   through App Group storage; the monitor extension never loads card data.
4. **DeviceActivity callbacks get missed** (documented across iOS 17–26). Every
   state is a timestamp window, and an idempotent `reconcile()` re-asserts the
   correct shield state on every app foreground and callback. Undocumented
   constants: 15-min schedule minimum, ~20 concurrent activities, 50 tokens per
   shield.
5. **App tokens are opaque and occasionally rotate** (acknowledged Apple bug).
   Stored selections are treated as a best-effort cache with a re-pick flow.

## Why FSRS-6 (not SM-2)

Same amount of state-machine code, dramatically better scheduling (see
`docs/research/15-research-srs-algorithms.md`), and the review log we persist
from day one makes per-user weight optimization possible later. Defaults:
desired retention 0.9, learning steps 1m/10m, relearning 10m, fuzz on.
